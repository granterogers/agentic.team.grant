# Run 2 — the bounded design (Stage C)

Principle: authorization first, approval second, and consolidate what exists. No second policy engine, no new workflow engine.

1. **The canonical unit** is an *effect*: `(tool, project, acting specialist or none, audience, exact-action fingerprint)`. The fingerprint is `sha256(stable json)` — the function `fingerprint()` in `checkpoint.ts` already exists and is what `job_pauses.binds_to` stores.
2. **One decision boundary: `app.authorize_effect(project, tool, job, staff, audience, fingerprint)`** (SQL, migration 0611). It CALLS `app.may_act` unchanged (the matrix, dial, standing rows and the "asked for" rule stay where they are) and layers what `may_act` cannot know. `mayAct()` in TypeScript keeps its name and gains optional `staff`, `audience`, `fingerprint`; it is the only door.
3. **Existing mechanisms**: `tool_permissions` (does the capability exist / is it on) and `autonomy_policy` (how far may the office go unasked) stay as inputs inside `may_act`. `standing_authorizations` stays an input (upgrades ask, never refuse). `app.may_act_outside` / `claim_delivery` stay **independent witnesses** — containment is not folded into authorization, because a witness that asks the same predicate as the guard cannot report the guard's blind spot (0603/0605).
4. **`staff_may_use` becomes a runtime input**: a step that names a specialist is refused unless `staff_may_use(specialist, tool)`. A step naming nobody is the office acting as itself, unchanged — enforcing it against the Chief of Staff would refuse `task.extract` and `drive.ingest`, which no staff member holds today, and granting those is Grant's decision, not this run's.
5. **Autonomy applies to consequential effects, not cognition.** `authorize_effect` is called only for effects (tools with `level ≥ 1` that write). Thinking, planning, consultation, delegation and drafting are not effects and never reach it.
6. **Outside audience is a floor**: `audience = 'outside'` can never resolve to `proceed` (not by dial, standing row or "asked for"): contacting another human always asks unless a future explicit policy changes it. `audience` is still only as trustworthy as its writer; it is a fail-safe direction (it can only add a question).
7. **`proceed | ask | refuse`** is produced by `authorize_effect`: refuse (unknown / off / dial says no / specialist lacks the grant / remembered refusal), ask (matrix says ask, or outside audience, and no exact approval on file), proceed (matrix, standing row, or the exact action was approved).
8. **An ask is bound to the exact action**: `blockers.action_fingerprint` (new column), written by `raiseBlocker` from the same fingerprint the pause stores. The ±10-second window in `answerFor` is replaced by an equality on that column.
9. **The answer binds back** through `app.hq_answer_blocker` only, which records `answered_option` and the verified principal (`answered_by`, new columns — the resolution text stays for people, and nothing parses it).
10. **A No is durable**: `raiseBlocker` names the declining option (`blockers.decline_option`, beside `standing_option`), `hq_answer_blocker` records which option was chosen, and `authorize_effect` REFUSES (not asks) an action whose fingerprint — or, for a duty, whose `(tool, project)` — was declined inside a window (`system_config` key `approval.refusal_days`, default 30). Distinct kinds: this exact action (fingerprint), the standing offer (tool + project), the whole objective (a job cancel — untouched, it is not a refusal), an alternative (a different fingerprint asks afresh), temporary ("Not now" uses the same window), expired (window elapsed → asks again).
11. **Duplicates and races** are already serialised by the `FOR UPDATE` in `hq_answer_blocker` (0596); restart is already handled by step checkpoints and `job_pauses`. Run 2 adds tests, not machinery, and one change: consumption is by step checkpoint, so an approval can never run an effect twice.
12. **Task-tick enters the same lifecycle**: `app.task_answers_blocker` no longer resolves the blocker itself; it calls `app.hq_answer_blocker` with the option the task carries and the principal recorded on the task (`tasks.completed_by`, new; written by `hq_task_state`'s new `p_by`, by the gateway from the verified credential and by chat from the command principal). A completion with no known principal reopens the task and leaves the question open (an external board pulling "done" cannot answer for Grant).
13. **Checkpoints and receipts** already prove what happened (`job_steps`, `satisfied.ts` requires a receipt for an acting plan). Unchanged.
14. **Migrations**: one, 0611 (columns, functions, trigger). Candidate-only; not applied to production in this run.
15. **Not in this run**: putting `notebook.generate`, `office.execute_plan`, `notion_import`, `notebook.add_source`, `tasks.sync` etc. behind `authorize_effect`. They are listed in the map as gaps (blocker-only or containment-only) and are the next boundary; doing them needs each handler's plan/dry-run, which is per-handler work.
