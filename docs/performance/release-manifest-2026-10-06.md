## 4. The smallest safe first production unit: migration 1023 alone

**Why this one.** It is one migration changing two functions, with no gateway or page dependency: today's gateway `thinking` section already calls
`office_health`, so 1023 reduces cost with no other change (MEASURED replica: 741,934 to 88,324 buffers; the largest per-call reader the page triggers).
It touches no table, row, index or column.

**Exactly what would happen** (after separate authorisation of every write, two consecutive GO canaries about ten minutes apart, and a clean `migrate:next` check):

1. `ALLOW_PRODUCTION_CHECKS=1 npx tsx scripts/rollout/step.ts 1023 precheck`: reads the live definitions of `app.office_health(uuid,integer)` and `app.last_progress(uuid)` and requires their normalised fingerprints to equal `pre` (80e53558..., 08da3080...). Anything else stops.
2. `ALLOW_PRODUCTION_WRITES=1 npx tsx scripts/rollout/step.ts 1023 apply --go`: re-runs the canary, re-checks, applies `migrations/1023_*.sql` (sha256 3298fd85...), runs the postcheck against `post` (e4049bbd..., 394fb674...).
3. The ledger row is written only with `record --go`, after the step is kept.

**How we would know it worked.** (a) `postcheck` reports both fingerprints equal to `post`. (b) The canary heartbeat stays inside its band. (c) The verdict
rule already approved: IMPROVED needs at least a 25% buffer-traffic reduction per hq-api request against the baseline; 15% to 25% is AMBIGUOUS (one extra pair, then "LIKELY IMPROVEMENT, BELOW PREDECLARED IMPROVED THRESHOLD"); within 15% is UNCHANGED.
The expected size on the replica is far above 25% for a call, but a production request mix is UNKNOWN, so the per-request figure may be smaller.

**How we would know it harmed anything.** WORSE per the approved rule: a startup timeout, a failed or slow heartbeat, 5xx above 2%, or `numbackends` more than 50% or 5 above baseline.
Functionally: the health card or the thinking indicator on a signed-in page erroring or showing a different state than before (the equivalence proof says the output is identical, so any difference is a defect).
The apply is a metadata-only `create or replace`; it takes a brief catalog lock, and a lock wait or timeout is itself a harm signal.

**Exactly how to roll back.** `ALLOW_PRODUCTION_WRITES=1 npx tsx scripts/rollout/step.ts 1023 rollback --go` applies `scripts/rollout/stabilisation/1023.rollback.sql`
(sha256 1eb7f2e6...), which restores the exact predecessor bodies (0750 and 0753), then verifies the `pre` fingerprints. If `record` was already run, follow with `unrecord --go`.
A rollback is never gated on health. Data: none changed, so nothing to restore. Time: seconds.

**What would NOT happen.** No other migration, no gateway or page deploy, no worker change, no `npm run migrate`, and no claim about the incidents. The next step (1027) is a separate approval.
