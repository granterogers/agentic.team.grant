## What I broke, and what happened about it

Three of these are mine and you should know about them.

### 1. `gmail.send` was enabled in the live database for about an hour

A check meant to prove *the app role cannot enable a policy-disabled tool* ran
through the Management API — which connects as a **superuser** — and its pass
condition accepted a successful `UPDATE` as a pass. It reported ✅ and left the
tool enabled. The neighbouring check looked like confirmation but was measuring
the level-3 approval rule, which returns `false` whether or not the tool is
disabled.

Restored by migration **0022**. The check now runs as `ai_team_app`, asks the
question that discriminates (refused *with* approval granted), has a control
proving it discriminates, and there is baseline drift detection so a silent
policy change is caught next run.

### 2. `research-director` spent a while running a prompt written by a test

The prompt-versioning checks demonstrated on a real permanent role. Repaired by
**0025** as version 3 — append-only and no-going-backwards do not get suspended
because the mistake was mine, so version 2 stays in the history as what it was.
The checks now use a fixture specialist and assert the roster is unchanged
before and after.

### 3. Fixture jobs had been leaking for several phases

`purge:fixtures` archived fixture projects and left their jobs **live**. By the
time the briefing generator ran for real it reported **63 jobs in flight**, all
debris. This matters more than untidiness: Today, Needs Me, the briefings and
`project_attention()` all read live jobs, so the leak made every summary in the
system wrong in the direction of "looks busy". Fixed, orphans swept, and the
purge report now shows live-job counts.

No test caught it for several phases because no test asked a question whose
answer depended on the total population. The feature that noticed was the first
one that summarised everything at once.

## The worker, and why it mattered immediately

Until the last hour of this session the system was all enforcement and no
engine: triggers refusing bad transitions, a router that cannot be called
without a duplicate scan, a review gate that cannot be bypassed — and nothing
that moved a job from `queued` to `complete`. Every guarantee was tested in
isolation and every suite was green.

The worker went in, and the first run found three defects that no isolated test
could have seen:

1. **The provider router never recorded usage.** §11 requires every inference
   attempt to be logged, failures included. The only caller of `recordUsage`
   was a POC script doing it by hand — so a rule that read as enforced was
   really one script's habit. Now recorded on all four exit paths.

2. **Crash recovery was a sweep to nowhere.** `recover_stalled_jobs` moves a
   stalled job to `retrying`; `dequeue_job` only reads `queued`. Migration 0006
   shipped `requeue_retrying` for exactly that gap and, like the sweep itself,
   had **no caller outside a test**. Two halves of one mechanism, each
   individually correct, with nothing joining them.

3. **`verify:jobs` leaked its capacity probes** — see the leak note above; this
   is the version that stops the queue rather than distorting a summary.

A real model call now goes `queued → committed → complete` through every gate,
on a free model, for $0.00. That is the first end-to-end proof the system has
had.

## The pattern that keeps recurring

Five phases in, the same defect keeps arriving in new costumes: **a check whose
result does not depend on the thing under test.** So far it has been a
hardcoded literal, a query against the wrong column, a test running as the
wrong role, an over-broad pass condition, an `UPDATE` matching zero rows, and —
the subtlest — a second safety mechanism arriving *in front of* the one under
test and silently retiring it.

There is now a seventh: **a fixture blocked by an earlier gate tests that gate,
not the one you meant.** A handler written to violate the determinism rule was
rejected by the coherence check first, so the check reported "no error" and
proved nothing about the trigger it was aimed at.

The sixth is worth reading about: `verify:ledger`'s TRUNCATE check has been
passing on the wrong mechanism since migration 0011 gave `inbound_commands` a
foreign key to `events`. Postgres now refuses TRUNCATE with `0A000` before the
statement trigger ever runs, so the trigger stopped being exercised while the
property stayed true. It is now two checks — the FK refusal, and
`TRUNCATE ... CASCADE` inside a rolled-back transaction so the trigger is
actually reached.

## Decisions made without you, that you might want to overturn

Each of these was a fork where I picked one road. None is hard to reverse.

1. **Learning proposes; it never applies.** The system can see you ignoring
   notifications and will write a `preference_proposal`, but nothing changes
   until something accepts it, and the app role cannot accept. The reasoning:
   if the inference is wrong, an auto-applied preference stops telling you
   things and *nothing surfaces that* — the only evidence is an absence. If you
   would rather it just adjusted quietly, that is a grant and a function away.

2. **Briefings call no model.** They are composed from counts. A model-written
   briefing is either unreviewed — and by §16 must not be relied on, defeating
   the point — or reviewed by somebody at 07:00. "3 things need you, 1 overdue"
   is a count, not a claim. They will read plainer than you might expect.

3. **An ambiguous project name asks rather than guessing.** "Switch to pricing"
   with two pricing projects resolves to *ambiguous*, not to the nearest match.
   A wrong project context is uniquely bad: everything afterwards looks normal
   and lands in the wrong place.

4. **Needs Me reports its overflow instead of truncating.** A list that
   silently shows 7 of 40 looks healthy exactly when it stops being useful.

5. **Autonomy starts at `suggest`.** Global default, set by migration. Raising
   it should be a decision you make, not something inherited from a default.

## Reproducing everything

```
npm run verify           # lint, typecheck, migrations, 427 unit tests, secret scan
npm run verify:db        # every live suite against Supabase, then purge fixtures
npm run verify:worker    # end to end through every gate — needs the queue to itself
npm run avatars          # regenerate the SVGs and the contact sheet
npm run avatars:png      # rasterise for Slack/Telegram
```

**If a verify script refuses to start**, read what it says: the queue is global
and small (three concurrent jobs), so two live suites cannot run at once, and
leaked jobs from a crashed run hold capacity until swept.
`npm run purge:fixtures -- --go` clears debris.

Evidence documents, one per phase, are in `docs/test-evidence/`. Each records
the defects found *by the checks failing*, not a list of passes — the failures
are the part worth reading.
