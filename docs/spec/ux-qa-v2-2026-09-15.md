## 0. NON-NEGOTIABLE FIRST-RUN EXECUTION CONTRACT

This first FULL UX QA run is a:
MINIMUM EIGHT-HOUR AUTONOMOUS WORK SESSION.
The intended behaviour is:
WORK CONTINUOUSLY AND AUTONOMOUSLY FOR AT LEAST EIGHT HOURS WITHOUT RETURNING CONTROL TO GRANT FOR ROUTINE QUESTIONS, PROGRESS REPORTS, PRIORITISATION, APPROVALS OR NEXT-STEP DECISIONS.
Eight hours is a minimum, not a maximum.
Do not intentionally waste time to satisfy the duration.
Continue doing useful work.

## 2. ONLY THESE CONDITIONS JUSTIFY EARLY INTERRUPTION

Before the eight-hour minimum, interrupt Grant only for:

A. Genuine external blocker
Further useful work is genuinely impossible because required credentials, permissions, infrastructure or an external service is unavailable AND no legitimate alternative work remains.
One unavailable tool or browser is not automatically a blocker.

B. Dangerous / irreversible action
The necessary next action risks:

* destroying real data
* exposing secrets
* meaningful financial cost
* irreversible production modification
* destructive external-service action

and genuinely requires owner approval.
Continue all independent work first.

C. Environment-forced termination
The Claude/runtime/environment itself prevents continued execution.
Before termination, persist complete continuation state.

* test failures

## 8. INSTALL THE TWO-LEVEL QA GOVERNANCE MODEL

The permanent system must distinguish ordinary QA from FULL UX QA.

### LEVEL 1 — PROPORTIONATE CHANGE-AWARE QA

Whenever user-facing UI/UX changes, automatically run QA proportional to blast radius.

#### LEVEL 1A — SMALL LOCAL VISUAL CHANGE

Examples:

* label
* icon
* local spacing
* local component styling

Minimum:

* static/smoke checks
* render actual changed surface
* exercise affected interaction
* visually inspect
* relevant viewport
* overflow check
* targeted accessibility
* regression for changed property

#### LEVEL 1B — INTERACTIVE CHANGE

Examples:

* dialog
* form
* menu
* conversation control
* call control
* Settings interaction
* task interaction

Add:

* real interaction
* keyboard
* focus
* console/network
* control coverage
* desktop + phone where relevant
* loading/error/empty states
* accessibility

#### LEVEL 1C — SHARED / BROAD CHANGE

Examples:

* navigation
* global CSS
* design tokens
* typography
* shared primitives
* project shell
* communications architecture
* auth
* theme
* Settings architecture

Add:

* representative route sweep
* layout verification
* phone overflow
* screenshot comparison
* themes
* reduced motion
* broader regression
* cross-screen visual coherence

### LEVEL 2 — FULL UX QA

Run only when:

* explicitly requested as FULL UX QA / deep UX audit / master QA;
* major redesign occurs;
* shared architecture changes have broad blast radius;
* a release warrants it;
* or systemic quality concerns justify it.

This first run IS Level 2.

## 9. CORE COMPLETION RULE

Persist this principle:
NO USER-FACING CHANGE IS COMPLETE UNTIL THE AFFECTED INTERFACE HAS BEEN RENDERED, EXERCISED AND VISUALLY INSPECTED IN A REAL BROWSER.
But also:
DO NOT RUN A MULTI-HOUR FULL AUDIT BECAUSE SOMEBODY MOVED A BUTTON FOUR PIXELS.
Test in proportion to risk.

## 10. FULL UX QA HAS TWO SUBJECTS

Audit BOTH:

A. THE PRODUCT
Does Agentic Team work and provide excellent UX?

B. THE QA HARNESS
Can the QA system actually detect failure?
A green test is not automatically trustworthy.

## 11. QA HARNESS SCEPTICISM

Do not trust:

* green tests with unexplained skips
* screenshots that were generated but never opened
* accessibility tests that exercise meaningless structure
* mouse-only mobile tests
* narrow desktop viewports masquerading as phones
* server-side fetches as proof of browser CORS
* teardown that never proved it removed anything
* tests whose results depend on execution order
* retries that hide semantic failures
* assertions that test implementation details instead of user-visible properties

For important QA mechanisms, safely demonstrate that the detector can fail.
Introduce a harmless temporary synthetic failure where practical.
Confirm red.
Restore.
Confirm green.
Never commit deliberate defects.

ZERO UNEXPLAINED SKIPS.

## 16. NEW: VISUAL DESIGN SYSTEM AUDIT

This is the major addition learned from Money Mastery.
Functional correctness is insufficient.
A product may:

* pass axe
* have no overflow
* have working controls

FULL UX QA must therefore audit visual coherence.

## 25. PHONE IS NOT A NARROW DESKTOP

## 45. FIXTURE POLICY

Before creating fixtures ask:
DOES THE LAYER UNDER TEST FILTER FIXTURES?
If yes, a fixture may be invisible to the exact layer being tested.
Use an isolated real test subject with teardown where necessary.
Otherwise use fixture naming/purge according to repository conventions.

## 46. TEARDOWN MUST PROVE CLEANUP

For integration tests:

1. clean stale test state safely
2. create unique test state
3. exercise
4. clean
5. assert cleanup matched something
6. assert no residue remains

Do not trust cleanup because a DELETE returned success.

## 47. LEAK CHECKS

Use current leak-detection tooling.
Never make real data disappear merely to turn a test green.
External destructive cleanup requires explicit safety.

## 48. SUITE ORDER INDEPENDENCE

Shared queues/services can create order-dependent tests.
Run important integration suites:

* independently
* after relevant neighbouring suites
* in different order where useful

Use scoped claiming.
Do not globally purge shared state as a lazy fix.

## 49. TIMEOUT IS NOT FAILURE

Classify:

* assertion failure
* external timeout
* killed worker
* network failure
* environment limitation
* residue
* actual product failure

Do not file the wrong defect.

## 50. COLD-START DEPLOY PROBES

* 503
* 504

* wrong 200 response
* auth failure
* CORS failure

## 60. AUTONOMOUS REPAIR LOOP

Do not stop after finding defects.
For each:
REPRODUCE -> ROOT CAUSE -> FIX -> REGRESSION -> BROWSER -> VISUAL INSPECTION -> BROADER CHECK
Then continue.

## 61. TEST USER-VISIBLE PROPERTIES

A regression should generally assert the thing the user experienced.
Examples:
Bad:
handler function exists
Better:
pressing the control produces the expected visible state
Bad:
heading-order helper returned true
Better:
meaningful heading navigation exists
Bad:
width is 390
Better:
actual touch-capable phone interaction works

## 62. DO NOT OVERFIT PRODUCT TO BROKEN QA

If a test is wrong:
fix the test.
Do not weaken correct product behaviour to make a stale assertion green.
Document the lesson where useful.

## 63. GITHUB ISSUES ARE PERSISTENT MEMORY

Material defects discovered during the run should become or update Issues.
Do not create hundreds of microscopic issues when they are manifestations of one systemic cause.
Prefer systemic issues with concrete evidence.

## 64. LIVE BACKLOG

Maintain:
P0 — broken, unsafe, misleading
P1 — major UX/design/system defect
P2 — substantial quality improvement
P3 — polish

Work primarily:
P0 -> P1 -> P2 -> P3
But prioritise high-leverage systemic fixes.
If the backlog becomes empty before eight hours:
AUDIT MORE DEEPLY.

## 65. PERIODIC DESIGN-DIRECTOR REVIEW

After several meaningful changes, stop coding briefly and inspect the product.
Ask:

* What currently looks worst?
* What feels like another product?
* What is too dense?
* What looks generic?
* What looks amateur?
* What is visually competing with the user's real work?
* What is repeated unnecessarily?
* Which inconsistency indicates a systemic problem?
* What single change would improve the largest portion of the product?

Then reprioritise.
Continue.

## 66. CHECKPOINT COMMITS

Do not hold eight hours of work in one diff.
Make logical commits.
Before meaningful checkpoints:

* relevant tests
* browser render
* interaction
* screenshot inspection
* regression
* HANDOVER/run-state update

Then continue immediately.

## 75. THE OPERATING PRINCIPLE

Do not trust the code.
Do not trust a screenshot you did not open.
Do not trust a green test that skipped half its controls.
Do not trust accessibility merely because axe returned zero serious violations.
Do not trust a heading-order test with only one heading.
Do not trust a mobile test that used a mouse.
Do not trust a narrow viewport that did not emulate touch.
Do not trust a retry that merely made a flaky deployment green.
Do not trust a suite that leaves debris in Grant's real projects or external services.
Do not trust teardown that did not prove it removed something.
Do not trust a test whose result depends on what ran before it.
Do not trust server-side fetch as proof of browser CORS.
Do not trust internal slugs as acceptable human project names.
Do not trust provenance simply because it exists if every simple human message looks like a database form.
Do not remove provenance merely to make the interface prettier.
Do not trust responsive until actual phone composition works.
Do not trust accessible until keyboard and screen-reader behaviour makes sense.
Do not trust visual QA until the image was actually looked at.
Do not trust an existing visual baseline to define good design.
Do not trust functional QA to tell you whether the product is beautiful.
Do not trust QA until you have demonstrated that QA itself can fail.

DO NOT RUN A TWO-HOUR DEEP AUDIT BECAUSE SOMEONE MOVED A BUTTON FOUR PIXELS.
Test in proportion to risk.
The objective is not maximal test volume.
The objective is:
MAXIMAL CONFIDENCE PER UNIT OF EFFORT.
