## Persistence and isolation findings (P0)

- **Where it lives.** Browser `localStorage` `bc.stage.<slug>` (this browser) mirrored to the office through `dashboard_layout_set` with
  `surface = 'basecamp'`, debounced 700ms and flushed on page hide. Server side the row is keyed
  `(owner, project_id, surface)`, `owner = app.office_actor(p_office)`, and the writer refuses a project that is not the caller's office
  (`migrations/0711`, `0582`). One office holds one person, so per user is per office; the sample office holds a guest.
- **Cross-user (replica, `scripts/isolated/layout-isolation.ts`, 16/16, rolled back).** Two people keep separate arrangements; one
  cannot save over, read through or reset the other by naming their project; a person's two surfaces are two rows; each project keeps its
  own; an empty arrangement is a reset; with the office check removed from a copy of the writer the isolation check turns red, so it can fail.
  NOT re-driven against production (the production guard refuses `check:ownership`, correctly; no flag was set).
- **DEFECT FOUND AND FIXED: two devices lost notes.** Notes were merged across tabs of one browser, but a device that had changed the
  arrangement never read the office again, so its next save erased notes written on another device. The page now folds the office copy's notes
  in at every refresh (the pulse) and when a tab returns after 30s (`layout.js adopt` merges notes only for a project this session has changed;
  view, sizes and positions stay as the session left them). Unit-tested, and the test fails without the fix.
- **Superseded by the third session (below): the first fix still left a window, and it is now closed except for the interleaving that needs
  a backend revision (#442).**
- **Residual.** The arrangement (view, sizes, positions) is last writer wins per person and project: it is one document. Two devices editing the
  same note at once: the newest edit wins, by each device's own clock (a badly wrong clock can make an older edit win). Strict compare-and-swap
  needs an additive backend change, filed as #442; it is NOT claimed fixed.
- **DEFECT FOUND AND FIXED: render loop at a restored zoom.** A persisted zoom other than 100% made the calendar module measure itself at the
  wrong scale on the first paint, flip size and redraw, about 45 redraws a second at rest. `--bc-zoom` is now in the first paint
  (`compose.js`). Found by `canvas-extremes` (mutation count at rest = 0); it hangs the check without the fix.
- **Coordinate limits, honestly.** The space is large, not unbounded: a module position and the pan clamp to +-100,000 logical px, a size to
  240..6,000 by 150..6,000, zoom 20%..250%. Hostile stored values (1e12, NaN, strings, zoom 1e9) draw without error and are clamped when
  drawn. Fit frames a spread of about 7,000px at most; a layout 200,000px wide (only a corrupt document can make one) is recovered by Tidy then Reset
  view. 126 items stayed above 60 frames a second.
