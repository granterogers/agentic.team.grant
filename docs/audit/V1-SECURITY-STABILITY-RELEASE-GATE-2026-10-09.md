## 3. Is there a confirmed production leak? **Confirmed replica vulnerability, production reachability unknown.**

I did not probe production: your production-read authorisation named specific release-inventory reads, not a security probe, and an unauthenticated read of other people's data is exactly the thing not to do without a separate yes.
The distinction the brief asked for: **a database SELECT privilege is not proof of API reachability, and I have not inferred a leak from the grant alone**; I have shown on a replica what the grant allows, and that is as far as the evidence goes.
**Exact bounded verification, prepared and NOT executed** (section 12, request R-A): three read-only steps that return no personal data: (1) the PostgREST configuration's exposed-schema list (Management API `GET /v1/projects/<ref>/postgrest`, metadata only); (2) `select rolbypassrls from pg_roles where rolname = 'postgres'` through the read-only endpoint; (3) one anonymous request for **zero rows** of the lowest-sensitivity view (`HEAD /rest/v1/delivery_health?select=channel&limit=0` with the public anon key, which is public by design and printed on the page): the status code decides it (200 or 206 means reachable; 401, 403 or 404 means not), no row is returned or read.

## 5. #458: the root cause, found by reproducing it
Class **D, a combination**, and not "flaky": three independent faults, each reproduced, each fixed, each given a regression that fails without the fix.
1. **Harness race (B).** The red was the control "the same words typed again later are a NEW message": 1 command instead of 2. Diagnostics added to the proof (steps, dock text, composer value, screenshot) captured it on the fifth whole-gate run: *"filled; box holds an empty string"* then *"clicked; box now empty"*: Playwright's `fill` landed on a composer that a redraw (a retry or answer landing) had just replaced, so the box a person would see was empty and the click sent nothing. A second signature under load: `click` on a submit button that was thrown away mid-action. CPU contention alone did not reproduce it (4 of 4 green with six busy loops); it needed the gate's parallel load. Fix: the helper puts the words in the live composer and submits its form in **one synchronous page step**, so no redraw can fall between; the real Send button is still pressed for the first message; no sleep was added and nothing asserted was weakened.
2. **Product defect: a redraw drops the keyboard.** `paintDock` rebuilds the composer on every redraw and kept the words but not the focus: a person typing while an answer, retry or history read lands lost every later keystroke (the new proof types a sentence across a held answer: **only `typi` of `typing as the answer lands on desktop` arrived**; the rest went to the page). Fix in `paintDock`: remember focus and cursor and restore them. Red without the fix at desktop and phone width (4 checks each), green with it.
3. **Product defect: a sent message can vanish from the screen.** `chat.load` dropped every in-flight message when a history read landed, including one typed **after the read began** (the read cannot contain it): the bubble disappeared until the next read, and a person types it again. (In the failing runs it showed as "the conversation did not include the message" after a resize.) Fix: drop only what was sent before the read started. The proof holds a history read for three seconds, sends meanwhile, and requires the message on screen once and in the office once; **0 times on screen without the fix**.
4. **Product defect: closing the dock threw the draft away.** Reopening showed the conversation and an empty box. Fix: the words are kept against the project they were typed for and restored only into that project's composer (never into another conversation), cleared on send.
